Todo list.  Open items only - finished work is in CHANGELOG.md and in the commit
messages that made the changes, not kept here.  Checks that need a person with a
device are in MANUAL_CHECKS.md, one line each here.  WIP.md holds the
longer-form handoff notes.

Cites name a symbol or a greppable string, not a file:line; a line number reads
as evidence while carrying none.  Each item is tagged with what the machine
picking it up has to have.

Two rounds ran on 2026-08-29.  The first had an SDK, an NDK and an API 36
emulator, and its results are in CHANGELOG.md's Verified section.  The second
had neither, and closed the four code items that headed this file - the C++
shim's drift from the shared original, R8's dishonest "Reading:" line, and the
terminal's two gaps.  They are gone from here and are in CHANGELOG.md.

What that second round could not do is watch any of it run, which is why
MANUAL_CHECKS.md gained a section and why the first item below is new.

NOBODY HAS UPGRADED A DEVICE ACROSS THE V0 MIGRATION, OR SEEN THE CATALOG FETCH
-------------------------------------------------------------------------------

- [ANDROID DEVICE or EMULATOR] the v0 disk-name migration renames the user's
downloaded images, the copies they have written to from inside CP/M, and the
four disk_slot_N preferences that name them, and it has never run anywhere but
in an argument.  V0MigrationTest covers the name mapping and both directories
against temporary directories on a JVM, and those 14 tests now pass under the
host recipe in CHANGELOG.md's 1.27 preamble - not under Gradle, which still
cannot start here.  What no harness can settle is an upgrade in place over real
pre-v0 state, external storage that is not there, and a restore from backup with
allowBackup on: MANUAL_CHECKS.md section 6 has all three, and says to build the
old state first, because a fresh install has nothing to migrate and passes every
one of them for free.

- [ANDROID DEVICE or EMULATOR] releases B and C - the two-level catalog and the
RomWBW release picker - have never fetched anything.  What has been done is one
step further than 1.26 managed and worth knowing before repeating it: every
Kotlin source in the app type-checks under kotlinc against real android.*,
androidx, okhttp and coroutines classes with only R, BuildConfig and
ActivitySettingsBinding stubbed, and all three JVM suites run and pass - 20
catalog parser tests, 14 migration tests and 3 JNI name-parity ones.
CHANGELOG.md's 1.27 preamble has the exact recipe; it needs no SDK.  What none
of it reaches is a device.  MANUAL_CHECKS.md section 7 has the six that need
one, and its check 2 is the one to do first: three new JNI bindings have no
build-time guard of any kind, so a Kotlin/C++ name mismatch shows up as
UnsatisfiedLinkError the first time Settings is opened and nowhere earlier.

- [ANDROID] DISK_NAMES_MIGRATION_PASS is 2 because release A shipped a flag
saying the rename was done while this build still downloaded pre-v0 names, so a
disk fetched under 1.26 could arrive after it.  Pass 2 sweeps those up.  There
should never be a pass 3: after this release the catalog publishes only v0
names.  If one is ever needed, that is evidence something started writing
pre-v0 names again, and the reason matters more than the sweep.

- [ANDROID] the bundled ROM is still the only ROM.  Selecting a RomWBW release
this build has no ROM for is allowed and confirmed with a warning, which is
honest but is not the same as being able to run it.  The catalog already
publishes roms[] with emu_avw and emu_rcz80 per release, and
emu_romwbw_release_of_image() can vet a downloaded one before it is offered -
but rom_name holds a bare filename that MainActivity opens with assets.open(),
so it needs a source discriminator (asset or downloaded file) before it can
name anything that is not inside the APK.  Until then, a 3.6.0 selection means
3.6.0 disks under a 3.5.1 ROM and the guest's mismatch warning.

- [ANY] tools/check-disk-pins.sh has diverged in this repo: the cpmdroid row is
now kind "index-v0" and asks a different question, because grepping for a
release tag that no longer exists made it print NO PIN FOUND and exit 1 for a
port that was working.  The other four copies - cpmemu, romwbw_emu, ioscpm,
z80cpmw - still hold the old version, and its own header says to edit one and
copy to the rest.  Copy it, and move the ioscpm and z80cpmw rows over as those
ports migrate.

- [ANY] romwbw_disks' published index-v0.json still carries a 3.6.0 note saying
no released client can load a v3.6.0 ROM because emu_validate_rom_hcb refuses
anything but the compile-time pin.  That was true before romwbw_emu v1.39 and is
not true now.  Nothing here branches on note text - the compatibility rules
forbid it - but a reader of the picker will find that note and conclude the
version list cannot work.  It needs fixing in the publishing repo.


THE PACKAGE IS BEHIND THE TREE
-------------------------------

- [RELEASE] nothing since 642b3b0 has shipped to anyone, and that gap is now the
only thing between this port and a release.  RELEASE_TAG is gone from
data/DiskCatalogRepository.kt entirely - the file names index-v0.json and takes
every URL from the documents it fetches - but that is a property of the tree,
not of any installed copy.  No release tag sits on or after 642b3b0; the newest
published one is v1.14 from 2026-01-16, from before that file existed.  So every
installed copy still fetches ioscpm v1.4.5 and still serves the pre-98eb6a1
w8.com and the R8 that hands an unfiltered host basename to F_DELETE.  What is
left is a build and a Play Store rollout.

  versionCode has moved 27 -> 29 and versionName 1.25 -> 1.27, which unblocks
  the upload.  28 / "1.26" names the disk-name migration alone and 29 / "1.27"
  the catalog repoint and the release picker; whether they go out as one upload
  or two, neither number is reused.  The history is worth keeping because it is
  how the block happened: both versionCode = 27 and versionName = "1.25" were
  already set at 35873d0, and at that commit DiskCatalogRepository.kt still read
  v1.4.5; the repin came after it in 642b3b0 and bumped neither number, so the
  build that would carry the pin could not go out under a number the published
  1.25 had already spent.  Any of these is spent the moment something is
  uploaded under it - check the App bundle explorer, not this file, before
  reusing one.
romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md owns the order and the reasons; read
it before publishing anything.  This app bundles no disk image -
app/src/main/assets holds emu_avw.rom and the help topics - so the image half
was, and stays, a release action in ioscpm.

  One thing the rollout does NOT fix, and the v0 rename makes it easier to
  miss rather than harder.  Nothing has ever invalidated an image already on the
  device: disks.xml's version attribute was 13 at v1.4.5 and 13 at v1.4.12
  alike, deliberately, because bumping it deletes the user's downloaded disks.
  hd1k_combo.img is the only one of the twenty whose bytes ever moved, and its
  sha256 is be19984e... at v1.4.5/v1.4.11, 89b8ae1a... at v1.4.12, and
  0ca4ec60... in catalog-v0-3.5.1.json - three different files under what used
  to be one name.  So a device that downloaded the combo under ANY ioscpm pin
  now has bytes that disagree with the v0 catalog, and after the rename they sit
  there under the v0 name with the catalog dialog showing a downloaded tick.
  The rename is still right - it is a rename, it loses nothing, and re-fetching
  49 MB uninvited is not the migration's decision to make - but the disagreement
  is now silent in a way it was not.  DiskDownloadManager.downloadDisk checks
  size and sha256 before replacing anything, but that guards a corrupt download,
  not a stale installed one.  Decide whether this port should re-fetch, or at
  least flag, an image whose installed hash disagrees with the catalog - the
  catalog now publishes a sha256 for every entry, so the check is a hash of a
  local file against a field that is already parsed.  Note that ioscpm has the
  identical hole.

- [ANDROID] the refreshed images are the only way to reach two paths this port
implements and has never executed: HBF_HOST_CAPS and HBF_HOST_GETNAME.  The
w8.com on the images today neither probes nor asks.  A local check is possible
without waiting for the release - romwbw_emu/disks/hd1k_combo.img already
carries the new r8.com and w8.com, and pushing it onto a device exercises both
- and that is worth doing before the images ship rather than after.

  Add HBF_HOST_GETRNAME (0xEA) to that list.  R8's "Reading:" line now has a
  real answer to print and nothing has ever printed it, and the interesting
  case is not the ordinary one: R8 asks between the open and the read loop, so
  the state is usually still HOST_FILE_WAITING_READ and the honest answer is
  "no answer" - meaning the line SHOULD show what was typed.  A run that shows
  the absolute path instead is not a pass, it is the race landing the other
  way, and it is worth knowing how often it does.


UPSTREAM, NOT HERE
-------------------

- [ROMWBW_EMU] emu_host_path_cap_name() in src/emu_io_common.cc can return the
empty string, and emu_io.h promises in as many words that it cannot: "a result
of "", ".", ".." or a bare drive letter is replaced by `fallback`".  The
head-keeping branch calls back_off_utf8() with no floor, so a component longer
than EMU_HOST_NAME_MAX whose first 255 bytes are continuation bytes backs all
the way to 0.  Reproducer:

    emu_host_path_basename(std::string(256, '\x80'), "download.bin") == ""

  The tail-keeping branch in the same function guards exactly this case, which
  is what makes it an omission rather than a design.  It matters most on a
  write: an empty leaf joined to an export directory names the DIRECTORY.  It
  reaches every port that calls the shared helper, and this one has a guard at
  its own call site (android_host_leaf) so that its copy of the function can
  stay byte-for-byte the original; delete that guard when the floor lands
  upstream and the copy is re-synced.


TERMINAL: WHAT IS STILL NOT THERE
----------------------------------

The parser gained VT52, DECSTBM, DECSC/DECRC, the query replies, ICH/DCH/ECH/
IL/DL/SU/SD, CHA/HPA/VPA, the three private modes, deferred autowrap and
per-cell attributes.  What is left is shorter than what went, and most of it is
absent from the siblings too - which is worth saying, because a gap all three
ports share is a different kind of item from one only this port has.

- [ANDROID] this port prints every byte from 0x20 up, where both siblings stop
at 0x7E.  So 0x7F (DEL) draws a glyph here and nothing there, and so does every
byte from 0x80 to 0xFF - which a CP/M program using the high half of a code page
will emit, and which arrives as whatever the JVM makes of the Char.  This
predates the terminal round and was found during its review; it is the last
divergence in the normal state.

- [ALL PORTS] none of the three has ENQ (0x05) answerback, CNL (CSI E), CPL
(CSI F), REP (CSI b), TBC/HTS, CBT (CSI Z), CHT (CSI I), origin mode (DECOM,
?6), an alternate screen buffer, left/right margins, a tab-stop table, charset
remapping, or OSC/DCS strings.  FF (0x0C) belongs on this list too: it is
discarded here, and neither sibling has a case for it either.  Nothing has
asked for any of them.  Listed so the next cross-port sweep can see they were
considered rather than missed.

- [DELIBERATE, do not report this as a gap again] SGR 0 resets the foreground
to Color.GREEN here, where ioscpm's applySGR and z80cpmw's both reset to CGA 7
light grey.  The green is this app's identity and the owner confirmed keeping
it on 2026-08-29.  DEFAULT_FG and DEFAULT_BG in TerminalView.kt carry the same
note.  A cross-port sweep will keep finding this; it is a divergence that was
chosen.

- [DELIBERATE] ESC[104m is light blue here and normal blue in z80cpmw.  That
port packs a cell into a CGA attribute byte whose background field borders the
blink bit and so folds 100-107 onto 40-47; a cell here is a full ARGB Int with
nothing to borrow, so the bright backgrounds stay bright.  Same asymmetry the
bright foreground range already had.

- [DELIBERATE] SGR 1 does not brighten the foreground here.  z80cpmw's bold
sets CGA bit 3, because in a packed attribute byte bold and bright ARE the same
bit and cannot be separated.  A cell here carries a full ARGB foreground and a
CELL_BOLD flag beside it, so ESC[1m picks the heavy face and leaves the colour
alone - which is what makes ESC[22m undo exactly what ESC[1m did.

- [DELIBERATE] SGR 39 and 49 work here and in neither sibling.  This is the one
divergence in the SGR handler that makes this port MORE conformant, not less,
and it predates the attribute work.


SCROLLBACK IS ROW 2, AND ROW 2 IS NOT LEVEL
--------------------------------------------

Found on 2026-09-02 from the other side: ioscpm's scrollback turned out never to
have captured a line in its life - its line-feed handler called scrollRegion(),
which shifts rows without keeping them, where only scrollUp() appends to the
buffer.  It was fixed there by moving the whole-screen test inside
scrollRegion() so no call site can miss it.  Reading the three ports side by
side to write that up turned up four things here.  None of them was found by a
device; all four are visible in this tree with grep.

Two of the four are closed: the snap-to-live and the keyboard-up rendering were
fixed on 2026-09-02 and are in CHANGELOG.md.  What is left is one deliberate
divergence and one small drawing bug.

- [DELIBERATE, corrected 2026-09-02] a cold boot keeps the previous session's
history, and this was written up here as a defect on the day it was found.  That
was wrong, and clear()'s own docstring says why: "The scrollback itself is
deliberately kept... losing the user's history is a product decision, not part of
putting the terminal back to power-on."  It even names how the siblings differ -
both drop it at the CALL SITE, z80cpmw's startEmulator and onEmulatorReset
calling resetScrollback beside clear(), ioscpm's reset() emptying its buffer -
which here would be MainActivity.  So the divergence is real and intentional, and
FEATURE_PARITY.md item 2's "history cleared on emulator start/reset" is a spec
line the three ports disagree on by choice rather than one of them being broken.
Left here as a decision someone may still want to revisit at the MainActivity
call site, not as a bug.  Worth noting how it was got wrong: the code said so in
a comment nobody read, which is the same failure the parity document made.

- [ANDROID DEVICE] the scrollback fixes of 2026-09-02 have not been watched
run.  There is no SDK, no kotlinc and no emulator on the machine that made them,
so what backs them is a brace-balance check, a line-by-line read against both
siblings, and a port of onDraw's windowing arithmetic to a scratch script that
reproduces the old keyboard-down behaviour exactly and shows the new keyboard-up
window reaching the top of the live screen.  None of that is a screen.  What to
point at it: drag back with the keyboard closed, then open the keyboard and drag
again; run a long DIR and confirm the view stays put while it prints; type a key
and confirm it returns to live; confirm the cursor is absent while scrolled back
and present at the bottom.


PARITY WITH THE OTHER PORTS
----------------------------

z80cpmw's FEATURE_PARITY.md describes this port from outside it, and README.md's
Related Projects section says which of these files back which rows.  After
changing them, run the reporter from here:
    sh ../z80cpmw/tools/check-sibling-drift.sh
It reads only, and exits non-zero when a column is behind the tree it describes.
Correcting a column is an edit in z80cpmw.

- [PARITY] rows 4, 6 and 13 were corrected in z80cpmw on 2026-08-29, and row 13
went from the row where this port was furthest behind to one where it is level
on everything the row measures.  What that edit could NOT do is advance the
sibling-readings block, and the reason is the document's own rule: that line
certifies a reading of the WHOLE column, and rows 4, 6 and 13 are three of
thirteen.  Whoever next reads rows 1, 2, 3, 5, 7, 8, 9, 10, 11 and 12 against
this tree can advance it; until then check-sibling-drift.sh will keep reporting
this column as drifted, which is correct.

- [PARITY] the two capabilities with no row - a bounded import and a receive
intent-filter - were folded into row 4 rather than given a fourteenth row.  Row
4's parity targets were already a lettered list and its heading already says
"arbitrary host paths + a findable data folder"; a new row would have renumbered
every "item 13" and "(#4)" cross-reference in a document that has dozens of
them.  If a future capability needs a row of its own, that is the cost to price.

- [PARITY] row 2's "Verified Android behaviour" block in z80cpmw's
FEATURE_PARITY.md cites five symbols that have never existed in this tree:
userScrollUp++, resetTerminal, historyIsContiguous, visibleHistorySize and
snapToLive.  grep finds none of them in app/src/main/java, and git log -S finds
no commit that ever removed them.  The paragraphs built on them assert the
opposite of what this port does - that the view stays anchored as output
arrives, and that history is cleared on a cold boot - which is how row 2 came to
be scored level while the three defects above were live.  Correcting it is an
edit in z80cpmw, and the useful correction is not just the five names: row 2 was
flipped from a paraphrase of ioscpm's commit message twelve minutes after that
commit landed, without either sibling's source being opened.  That is the thing
worth not repeating.
