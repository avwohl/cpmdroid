- the bundled disk images still carry the pre-98eb6a1 w8.com and r8.com, so
nothing this port gained from the v1.36 core is visible to a user yet.  W8
neither probes HBF_HOST_CAPS (0xE9) nor asks HBF_HOST_GETNAME (0xE8), so the
capability bit this port now asserts and the Exports path it now reports both
go unread; W8 still truncates a binary export at the first 1Ah byte; and the
old R8's ambiguous-FCB bug, which erases every matching CP/M file before
creating the new one, is still live.  READ
romwbw_emu/docs/RELEASE_ORDER_2026-08-25.md BEFORE PUBLISHING ANYTHING: the
refresh is what arms a data-destruction bug in ioscpm, so the port fixes go
first, refreshed images must never be attached to the existing v1.4.5 tag
(DiskCatalogRepository.kt:27 pins it, and every installed app would start
fetching them with no update), and no image whose w8.com lacks the 0xE9 probe
may be published to any tag.  cpmdroid is step 2 of that plan; the code half is
done as of this round.

- the zero-byte export fix has never been compiled by the NDK or run anywhere.
emu_host_file_close_write() no longer demands a non-empty buffer, the JNI hands
back a zero-length array where it used to hand back null, and
handleHostFileWrite() now treats an empty array as a file to create
(CHANGELOG.md, Unreleased / Fixed).  the machine it was written on has no SDK,
NDK, Gradle or javac; what stands behind it is a host build of
emu_io_android.cpp against a stub jni.h, the real headers and the real core
objects, driven through an export, and the Kotlin line was read rather than
compiled.  before publishing: W8 an empty CP/M file on an API 36 AVD, confirm a
zero-byte file appears in Exports, and confirm a normal export still carries
all of its bytes.  ioscpm has the same bug in the same shape at
emu_io_ios.mm:483 and it is not fixed there.

- W8 exports still cannot leave the sandbox by a path, and R8 imports still
cannot arrive by one - both are reduced to a leaf inside Imports/ and Exports/.
That is the right shape for Android and it is deliberate, but it is also
FEATURE_PARITY item 4(a), which is open in BOTH directions here: a real save-as
on export (ACTION_CREATE_DOCUMENT) and a real picker on import
(ACTION_OPEN_DOCUMENT or GetContent) are equally missing.
  this entry used to say the export half was the only one left, "to sit beside
the Import File... picker that already covers arrival by staging".  There is no
such picker and there never was one here.  Checked at 9b68ab1: no
registerForActivityResult, no ACTION_OPEN_DOCUMENT, no ACTION_CREATE_DOCUMENT,
no GetContent and no DocumentFile anywhere under app/src/main/java, and
AndroidManifest.xml has only MAIN/LAUNCHER - no share and no view
intent-filter, so a file cannot arrive from another app either.  Arrival works
because the user copies the file into Imports/ with a file manager, which is
what README.md:47 tells them to do, and on Android 11+ the stock Files app does
not show Android/data at all, so even the staging is a fight.  "Import File..."
is an ioscpm feature (iOSCPM/Views/ContentView.swift:231); it was read into
this port's column by the same 2026-08-07 pass that FEATURE_PARITY has already
corrected, and its Android cell says the same thing this entry now says.
