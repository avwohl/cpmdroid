BEFORE ANYONE ADDS DISK-IMAGE HASH VERIFICATION, READ THIS
-------------------------------------------------------------------------------

- [ANY] no disk image already on the device is ever hashed.  The catalog
document's sha256 is verified, and a download's bytes are verified as they
arrive, but nothing re-reads an installed file: isDiskDownloaded() decides by
filename.  That is
why the v0 migration needed no freshness work here, and it is also a trap for
whoever adds image verification later.
  hd1k_combo is the one image of twenty whose bytes differ between the pre-v0
catalog and catalog-v0-3.5.1.json, and the migration renames rather than
re-downloads, so every migrated device holds it under a hash the catalog does
not name.  It is not corrupt: the two images were compared byte for byte on
2026-09-05 and slice 0's directory lists the same 94 files, all 94 extract
byte-identical including r8.com and w8.com, slices 1-5 do not differ at all, and
the 2,342 bytes that do differ are CP/M slack between the files.  Two toolchains
wrote the same disk.
  So a naive "hash mismatch means re-download" would hand every migrated user a
49 MB download for nothing.  ioscpm and z80cpmw both carry the fix already -
CatalogMigration.equivalentPriorImage and diskv0::isEquivalentPriorImage, keyed
on provenance so that only the migration can produce it and a fresh download can
never be blessed by it.  Copy that shape rather than inventing one.
  romwbw_disks docs/FINDINGS.md section 10 has the measurements.

- [ANDROID] an image downloaded before the v1.4.12 repin keeps the destructive R8 and
there is no way out of it from inside the app.  That r8.com copies the host basename
into the FCB unfiltered, so '?' and '*' make it ambiguous and F_DELETE runs before
F_MAKE: importing a?b.txt erases every CP/M file matching A?B.TXT first and says
nothing (romwbw_emu CHANGELOG, "R8 erased unrelated CP/M files" - verified live, two
unrelated files went).  Downloads only happen for an ABSENT file, so the repin does
not refresh what is already there.  This port has no DiskLedger and no
refreshSuperseded, and deleteDisk()/deletePersistedDisk() in DiskDownloadManager.kt
have no caller anywhere under app/ - the Settings X is clearDiskSlot(), which sets the
slot to null and leaves the file on the device.  Reinstalling is the only remedy a
user has.  ioscpm solves this with a ledger keyed on provenance - the catalog sha256
a verified download matched - not on hashing the installed file, because a downloaded
disk is a writable volume the guest rewrites and that comparison calls every disk a
user has saved work into stale.  DiskLedger.action is the shape: refresh unasked only
when superseded AND pristine, offer when it would be lossy, stand down while the
emulator holds the file open.  Copy that rather than inventing one.

- [ANDROID] a ROM is never deleted, including a bad one.  A file that fails
verification is re-downloaded once, and the fetch renames a fully verified
transfer over it - so a failed attempt leaves what was there rather than leaving
nothing, and a ROM a user put in that directory themselves is never removed.
The cost is an unused 512 KB file per withdrawn release, which nothing reclaims.
That is the deliberate side of the trade; if it ever becomes a complaint, the
answer is a user-initiated cleanup, not an automatic one.

  case is not the ordinary one: R8 asks between the open and the read loop, so

A GUARD HERE THAT STANDS IN FOR A MISSING FLOOR UPSTREAM
--------------------------------------------------------

- [ANDROID] android_host_leaf() carries a floor that the function it guards does
not, and deleting that guard is a re-sync rather than an edit to make on its own.
android_host_path_cap_name() is this port's copy of romwbw_emu's
emu_host_path_cap_name(), kept in step with it on purpose so a drift sweep finds
nothing to file, and the head-keeping branch it copied backs a cut off
continuation bytes with no floor: a component longer than EMU_HOST_NAME_MAX whose
first 255 bytes are continuation bytes backs all the way to 0 and the function
answers "", where emu_io.h promises in as many words that it cannot - "a result
of "", ".", ".." or a bare drive letter is replaced by `fallback`".  Confirmed by
compiling and running romwbw_emu's own source on 2026-09-13, g++ -std=c++17, not
reasoned about: the head branch returns 0 bytes and the tail branch, which has
the guard, returns 255.  Note while re-syncing that the guard's own comment calls
this copy "byte-for-byte the shared function" and it is not - the logic matches,
the indentation and the comment wrapping do not, so diff the two by hand rather
than trusting either sentence.

  It matters on the write side only.  An empty leaf makes
  g_host_write_destination the Exports FOLDER, and opening that path for writing
  asks the filesystem to truncate a directory; the read path passes "" as its
  fallback deliberately, since an empty name means "no preference" to the
  bare-FCB R8, so the guard is a no-op there.  Nothing shipped reaches it today
  because R8 and W8 both build the path in a 128-byte buffer - a property of the
  .com files on today's images, not of this function's contract.
  The floor belongs in the shared helper, and romwbw_emu's todo.txt is where
  that is recorded; when it lands, this guard comes out with the re-sync.


TERMINAL: WHAT IS STILL NOT THERE
----------------------------------

The parser gained VT52, DECSTBM, DECSC/DECRC, the query replies, ICH/DCH/ECH/
IL/DL/SU/SD, CHA/HPA/VPA, the three private modes, deferred autowrap and
per-cell attributes.  What is left is shorter than what went, and most of it is
absent from the siblings too - which is worth saying, because a gap all three
ports share is a different kind of item from one only this port has.

- [ANDROID] this port prints every byte from 0x20 up, where both siblings stop
at 0x7E.  So 0x7F (DEL) draws a glyph here and nothing there, and so does every
byte from 0x80 to 0xFF - which a CP/M program using the high half of a code page
will emit, and which arrives as whatever the JVM makes of the Char.  This
predates the terminal round and was found during its review; it is the last
divergence in the normal state.

- [ALL PORTS] none of the three has ENQ (0x05) answerback, CNL (CSI E), CPL
(CSI F), REP (CSI b), TBC/HTS, CBT (CSI Z), CHT (CSI I), origin mode (DECOM,
?6), an alternate screen buffer, left/right margins, a tab-stop table, charset
remapping, or OSC/DCS strings.  FF (0x0C) belongs on this list too: it is
discarded here, and neither sibling has a case for it either.  Nothing has
asked for any of them.  Listed so the next cross-port sweep can see they were
considered rather than missed.

- [DELIBERATE, do not report this as a gap again] SGR 0 resets the foreground
to Color.GREEN here, where ioscpm's applySGR and z80cpmw's both reset to CGA 7
light grey.  The green is this app's identity and the owner confirmed keeping
it on 2026-08-29.  DEFAULT_FG and DEFAULT_BG in TerminalView.kt carry the same
note.  A cross-port sweep will keep finding this; it is a divergence that was
chosen.

- [DELIBERATE] ESC[104m is light blue here and normal blue in z80cpmw.  That
port packs a cell into a CGA attribute byte whose background field borders the
blink bit and so folds 100-107 onto 40-47; a cell here is a full ARGB Int with
nothing to borrow, so the bright backgrounds stay bright.  Same asymmetry the
bright foreground range already had.

- [DELIBERATE] SGR 1 does not brighten the foreground here.  z80cpmw's bold
sets CGA bit 3, because in a packed attribute byte bold and bright ARE the same
bit and cannot be separated.  A cell here carries a full ARGB foreground and a
CELL_BOLD flag beside it, so ESC[1m picks the heavy face and leaves the colour
alone - which is what makes ESC[22m undo exactly what ESC[1m did.

- [DELIBERATE] SGR 39 and 49 work here and in neither sibling.  This is the one
divergence in the SGR handler that makes this port MORE conformant, not less,
and it predates the attribute work.


SCROLLBACK IS ROW 2, AND ROW 2 IS NOT LEVEL
--------------------------------------------

Found on 2026-09-02 from the other side: ioscpm's scrollback turned out never to
have captured a line in its life - its line-feed handler called scrollRegion(),
which shifts rows without keeping them, where only scrollUp() appends to the
buffer.  It was fixed there by moving the whole-screen test inside
scrollRegion() so no call site can miss it.  Reading the three ports side by
side to write that up turned up four things here.  None of them was found by a
device; all four are visible in this tree with grep.

Two of the four are closed: the snap-to-live and the keyboard-up rendering were
fixed on 2026-09-02 and are in CHANGELOG.md.  What is left is one deliberate
divergence and one small drawing bug.

- [DELIBERATE, corrected 2026-09-02] a cold boot keeps the previous session's
history, and this was written up here as a defect on the day it was found.  That
was wrong, and clear()'s own docstring says why: "The scrollback itself is
deliberately kept... losing the user's history is a product decision, not part of
putting the terminal back to power-on."  It even names how the siblings differ -
both drop it at the CALL SITE, z80cpmw's startEmulator and onEmulatorReset
calling resetScrollback beside clear(), ioscpm's reset() emptying its buffer -
which here would be MainActivity.  So the divergence is real and intentional, and
FEATURE_PARITY.md item 2's "history cleared on emulator start/reset" is a spec
line the three ports disagree on by choice rather than one of them being broken.
Left here as a decision someone may still want to revisit at the MainActivity
call site, not as a bug.  Worth noting how it was got wrong: the code said so in
a comment nobody read, which is the same failure the parity document made.

- [ANDROID DEVICE] the scrollback fixes of 2026-09-02 have not been watched
run.  There is no SDK, no kotlinc and no emulator on the machine that made them,
so what backs them is a brace-balance check, a line-by-line read against both
siblings, and a port of onDraw's windowing arithmetic to a scratch script that
reproduces the old keyboard-down behaviour exactly and shows the new keyboard-up
window reaching the top of the live screen.  None of that is a screen.  What to
point at it: drag back with the keyboard closed, then open the keyboard and drag
again; run a long DIR and confirm the view stays put while it prints; type a key
and confirm it returns to live; confirm the cursor is absent while scrolled back
and present at the bottom.


- [ANDROID] the catalog index is switchable in the model but has no UI yet.
SettingsRepository now carries KEY_CATALOG_INDEX_URL (empty = the index this
build ships with), resolveIndexUrl/isCustomIndex/fnv1a32, and the instance
accessors catalogIndexUrl, effectiveIndexUrl, usingCustomIndex and
indexUrlIsFromEnvironment.  $ROMWBW_INDEX_URL wins over the setting for one run,
which is what a test uses and what works TODAY with no UI:

    adb shell setprop ... is not it - use the run configuration's environment,

  Everything a switch has to move moves with it.  scope() appends indexScope to
